## 1. Цель

Создать локальную интерактивную академию кибербезопасности для одного владельца.
Сервер и база работают на Windows-ноутбуке, существующие учебные контейнеры
Docker Desktop остаются целями, а команды ученика выполняются в отдельной Linux
VM. Проверка результата детерминирована и не зависит от AI.

Главная единица обучения представляет доказанный цикл:

```text
термин -> пример -> прогноз -> действие -> наблюдение -> объяснение
-> вопрос наставника -> исправление и debrief -> evidence -> повторение
```

Навык меняет состояние только после полного цикла и может дойти до
`independent`. Этап `transfer` применяется только к навыкам с Docker-целями и
требует успешного повтора на второй цели с другим fingerprint.

## 2. Части системы

| Часть | Назначение |
|---|---|
| Windows host | Единственный сервер, основная база, Studio и точка доступа по домашней сети. |
| FastAPI backend | API, роли устройств, сессии, graders, Docker discovery, relay, SSH terminal, импорт и поиск. |
| React frontend | Адаптивная академия для Windows, Mac, планшета и телефона. |
| SQLite + FTS5 | Курсы, сессии, evidence, reviews, устройства, targets, заметки и поиск. |
| Docker Desktop adapter | Только читает состояние существующих контейнеров и опубликованные порты. |
| Training Relay | Временно проксирует TCP от точного IP Linux VM к loopback-порту выбранного контейнера. |
| SSH adapter | Открывает shell `student` и строго ограниченные probes `range-runner`. |
| Deterministic grader | Проверяет зарегистрированную команду и структурированное наблюдение. |
| Методический наставник | Возвращает локальный сократический вопрос по фактам run, не влияет на verdict. |
| Studio | Создаёт content-addressed read-only snapshot, source blocks и проверяемый черновик. |
| Windows packaging | Формирует self-contained installer приложения и doctor. |

Внешние Codex CLI и Claude Code не входят в активный Windows-релиз. Исходный код
экспериментальных adapters сохраняется за выключенным флагом, но Windows всегда
отклоняет их запуск, потому что текущая модель изоляции не доказывает отсутствие
чтения других локальных файлов.

## 3. Контракты компонентов

### Backend API

- Вход: JSON API, multipart imports, WebSocket terminal, curriculum files и SQLite.
- Выход: JSON, WebSocket frames и статический production frontend.
- Аутентифицированные изменяющие операции требуют разрешённую роль и CSRF token.
- Единственное исключение по CSRF: первичное `POST /devices/pair`, где ещё нет
  сессии. Оно требует одноразовый 10-минутный secret и точный fingerprint.
- Pairing secret потребляется атомарно; параллельный второй запрос отклоняется.
- Ошибки имеют структуру `{code, message, details, trace_id}` без секретов.

### Docker Desktop adapter

- Вход: `docker version`, `docker context inspect`, `docker ps`,
  `docker inspect` и `docker port` с timeout.
- Выход: нормализованные `DiscoveredTarget[]`.
- Adapter не выполняет `run`, `start`, `stop`, `restart`, `rm`,
  `compose up/down`, pull, удаление volume или изменение Docker settings.
- TCP Docker daemon на `2375` не включается.

### Training Relay

- Вход: подтверждённый `TargetProfile`, точный IP Linux VM и свободный порт из
  диапазона `47000..47100`.
- Выход: временный relay endpoint и lifecycle state.
- Relay принимает TCP только от указанного IP Linux VM.
- Назначение всегда берётся из подтверждённого loopback endpoint target profile.
- Relay закрывается при stop, reset, TTL или остановке приложения.

### SSH terminal и range-runner

- Интерактивный shell открывается только для `student` с закреплённым SSH host key.
- Bootstrap от root отклоняет любую запись `student` в полном sudo policy. Перед
  lab backend повторно отклоняет доступный `sudo -n -l`, `sudo -n true` и чтение
  или запись известных system/rootless Docker sockets.
- Один lab run имеет не более одной активной terminal session.
- Backend регистрирует отправленные terminal commands отдельно от transcript.
- `range-runner` не получает общего shell, PTY или forwarding. Он принимает
  `tools`, TCP probe relay, `nmap -sV -Pn` одного разрешённого порта и HTTP GET
  через relay. Host и port не берутся из curriculum в обход профиля.
- HTTP probe возвращает только структурированные метод, path, status и наличие
  заголовка. Body, cookie, token и значение заголовка не возвращаются grader.

### Deterministic grader и evidence

- Grader получает lesson specification, зарегистрированные commands,
  структурированное probe-наблюдение, target fingerprint и артефакты текущего run.
- Результат observation gate: `passed|failed|needs_evidence` с адресными причинами.
- Текст transcript сам по себе не доказывает факт. Поддельный `printf` не проходит
  target probe и не создаёт evidence.
- После observation pass ученик обязан сохранить объяснение, получить локальный
  вопрос наставника и записать исправление/debrief.
- Только `POST /lab-runs/{id}/finalize` создаёт evidence и завершает run.
- Повторный finalize того же run не создаёт дубликат evidence или review.
- Завершённый due review закрывается; создаётся или обновляется один следующий.
- Каждый успешный evidence продвигает skill не более чем на одну ступень.
- `transfer` разрешён только для target-backed навыка, из `independent` и при
  двух разных fingerprints. Практики только в Linux VM завершают рост на
  `independent`.
- Любой AI-ответ исключён из входов grader и не может изменить verdict.

### Studio

- Вход: DOCX, MD, TXT, LOG, PNG, JPEG или TIFF.
- Выход: content-addressed snapshot, SHA-256, source blocks, deterministic draft
  и validation report.
- Исходный пользовательский файл не редактируется.
- Snapshot переводится в read-only mode и повторно проверяется по SHA-256 перед
  публикацией. Это обнаруживает изменение, но не заявляет аппаратную immutable FS.
- OCR выполняется локально. Публикацию выполняет только `owner`.
- AI-generated draft в первой Windows-версии не используется.

- `SourceBlock`: source id, ordinal, page/paragraph reference, extracted text.
- `Draft`: source coverage, `draft|validated|published`, content.

На Windows приватные ключи и локальные secrets защищаются DPAPI для текущего
пользователя. Development fallback явно маркируется и не допускается installer.

## 5. Сценарии

### Первый запуск на Windows

Пользователь устанавливает приложение. Doctor проверяет Windows, Docker, сеть,
SQLite и Linux VM. Discovery только читает контейнеры. Owner подтверждает target
profile. Backend проверяет loopback endpoint, SSH boundary и маршрут
`Linux VM -> relay -> target`. Lab остаётся заблокированным, пока эти проверки
не пройдут.

### Учебная сессия

Пользователь выбирает 15, 45 или 90 минут. Backend заполняет этот timebox суммой
оценочных длительностей уроков, сохраняет план и связанную
`LearningSession`. Страница урока переиспользует эту session. Ученик делает
прогноз и вводит утверждённую команду первой командой чистого lab run. После
эксперимента явный reset создаёт новый run. Ученик проходит observation gate, объясняет факт, получает
сократический вопрос, записывает исправление и debrief. После finalize создаются
evidence и следующий review. Session получает `completed`, когда завершены все
уроки плана. Девяностоминутный план завершает маршрут evidence-report уроком, но
сам по себе не обещает `transfer`.

### Доступ с Mac и телефона

Только после полного LAN/HTTPS preflight owner создаёт token, который живёт
10 минут. QR содержит только token. Пользователь
отдельно сверяет certificate fingerprint с Windows-экраном и вводит его вручную.
После атомарного потребления token Mac получает выбранную роль, телефон обычно
получает `viewer`. Viewer не может вводить terminal commands, запускать lab,
управлять relay/Docker, публиковать Studio draft или менять system settings.

### Studio

Owner импортирует файл. Backend копирует его, пишет SHA-256, извлекает source
blocks и переводит snapshot в read-only mode. Deterministic template создаёт
draft. Validator проверяет hash, read-only state, покрытие и ссылки. Owner вручную
публикует новую версию. Пользовательский оригинал не меняется.

## 8. Готово, когда

1. Backend и frontend собираются, типизируются и проходят tests.
2. Чистая база, FTS5 virtual tables и triggers создаются frozen Alembic migration;
   downgrade удаляет всю application schema, runtime подтверждает revision и integrity.
3. Docker discovery распознаёт published ports и предупреждает о `0.0.0.0`, не
   выполняя mutating Docker command.
4. Relay принимает только точный IP Linux VM и закрывается при stop, reset, TTL
   и shutdown.
5. SSH terminal поддерживает input, output, resize, reconnect и transcript.
6. Lab блокируется при unsafe `student` sudo/Docker boundary.
7. `range-runner` отклоняет произвольную shell command и не раскрывает body/secrets.
8. Viewer получает 403 на terminal input, relay, lab mutations и Studio publish.
9. Для transcript-grader approved command должна быть первой shell-командой нового
   lab run. Gateway фиксирует ledger и input offset, поэтому вывод более раннего
   процесса не может попасть в зачётную попытку. После любой пробной команды ученик
   запускает явную чистую попытку. Evidence появляется только после explanation,
   tutor question и correction/debrief.
10. `transfer` нельзя получить на том же target fingerprint или прямым прыжком.
11. Ошибка TCP/HTTP не описывается как полученный HTTP response.
12. Review закрывается после успешного повторения, без вечных дубликатов.
13. Studio сохраняет original SHA-256, обнаруживает mutation и не публикует без owner.
14. Внешний AI на Windows fail-closed и не является обязательной зависимостью.
15. Нет page overflow на 360, 390, 480, 768, 1024, 1366, 1440, 1920 и 2560 px.
16. Windows package запускается без отдельно установленных Python, Node.js и Git.
17. Реальный пилот подтверждает Windows -> Docker, Windows -> Linux SSH,
   Linux VM -> relay -> Docker, Mac -> academy и phone viewer.
18. v1 восстанавливается по tag/backup; в v2 импортируются только Field Notes с
   source id и source hash.

Фактический статус каждого gate ведётся в
[`docs/acceptance-status.md`](docs/acceptance-status.md). Официальные основания
технических утверждений находятся в
[`docs/official-sources.md`](docs/official-sources.md).

## 9. Расширение v2.1: повторение команд из CyberLabs

Статус: согласовано 27.08.2026, реализуется Этап 1 (9.6). Рабочее
предположение: развиваем v2 (сервер и интерфейс на Windows/Mac), старый Mac-v1 не
развиваем параллельно. Цель расширения: ученик вспоминает подходящую команду из
уже пройденных CyberLabs, применяет её в новой ситуации, объясняет результат и
возвращается к приёмам, которые забывает. Перечитывание документов перестаёт быть
обязательным входом в занятие. Отсутствие забывания не обещаем: система замечает
затруднение и возвращает соответствующую практику. Метод повторного извлечения
из памяти опирается на Roediger и Karpicke, Psychological Science 2006 (короткая
цитата: «prior testing produced substantially greater retention than studying»,
[статья](https://learninglab.psych.purdue.edu/downloads/2006/2006_Roediger_Karpicke_PsychSci.pdf)).
Исследование проводилось на текстах, перенос на команды полигона это проектная
гипотеза, проверяемая первым прохождением.

### 9.1 Проверенный контекст

Сверено с диском 27.08.2026, эти факты обязательны для реализации:

- Источник команд: 27 мнемоник в `~/Desktop/СуberLabs`, из них 11 Linux
  (01-07, 09-12) и 16 Windows (01-03, 05-17). Linux 08 и Windows 04 отсутствуют и
  не выдумываются. Всего в папке 75 DOCX, включая архивы и вспомогательные файлы.
- Мнемоники текстовые: команды лежат в параграфах и таблицах, встроенных
  изображений в проверенных файлах нет. Значит для мнемоник OCR и извлечение
  картинок из DOCX не требуются, их извлекает существующий Studio. Изображения и
  OCR нужны только скриншотным Task-источникам, это отдельный поздний этап.
- Планировщик [`services/curriculum.py`](backend/src/cyber_range_coach/services/curriculum.py)
  (`Curriculum.plan`) отбирает уроки по кортежу `score`, где первым идёт сумма
  минут, а число просроченных повторений только тай-брейк. Поэтому текст
  интерфейса «повторение просрочено» опережает фактический приоритет. Расширение
  делает приоритет просроченного безусловным.
- Планировщик перебирает `combinations` уроков. На каталоге команд это
  комбинаторный взрыв, переносить перебор нельзя.
- Grader [`services/grader.py`](backend/src/cyber_range_coach/services/grader.py)
  (`_same_command`) нормализует все пробелы и сравнивает регистронезависимо. Для
  каталога команд это неверно: пробелы внутри кавычек значимы, регистр Linux-команд
  значим. Существующий grader для текущих 19 уроков не ослабляем, для повторения
  команд вводим отдельный контракт.
- Studio извлекает текст (параграфы и таблицы), публикует JSON, а учебный
  загрузчик читает YAML. «Загрузить DOCX в Studio» не равно «получить уроки»,
  между ними нужен явный мост «source block -> приём -> YAML-урок».
- `ReviewItem` связан только со `skill_id` и `lesson_id`, истории отдельной
  команды в модели нет.

### 9.2 Новые части

| Часть | Назначение |
|---|---|
| Каталог приёмов | `CommandTechnique`: команда с оболочкой, назначением, значимыми флагами, типичной ошибкой, образом мнемоники и адресом в источнике. Linux `find` и Windows `find` это разные приёмы. |
| Подготовка контента | Переиспользует Studio snapshot, хэши и адреса блоков, добавляет маппинг «блок -> приём» и таблицу покрытия. Скриншотные источники получают извлечение изображений и OCR отдельно. |
| Практика | Внутри существующих Today, Lesson и Lab: короткое повторение в начале, миссия, панель каталога рядом с заданием без обязательного перехода в справочник. |
| Учёт команд | В существующей SQLite: история попыток вспомнить и применить приём, раздельно по видам достижения. |
| Grader миссий | Отдельная проверка новых миссий, не смешивается с текущим transcript/probe grader. |

### 9.3 Контракты компонентов

**Recall grader (воспроизведение команды).** Вход: ответ ученика и контракт
конкретного задания. Ответ никогда не исполняется как shell-команда. Проверка
учитывает кавычки и регистр Linux-команд, допустимые варианты (например
перестановка независимых флагов) задаются в контракте задания, а не общей
нормализацией. Выход это различимая причина: верно; верно с помощью; неверный
инструмент; неверный флаг; другая оболочка; недостаточно данных. Отдельный вопрос
«что означает эта строка вывода» проверяет понимание наблюдения, а не синтаксис.

**Mission grader (новые миссии), версия 1.** Проверяет финальный артефакт задачи
(найденная строка, файл или значение) детерминированной проверкой результата плюс
объяснение через наставника. Проверка полной последовательности команд отложена до
отдельного контракта. Заявленные корректные варианты допускаются, поддельный вывод
не принимается, неизвестный вариант возвращает «нужна проверка», а не ложный успех.
Существующий transcript/probe grader и его границы не ослабляются.

**Планировщик повторений.** Greedy-отбор по приоритету: сначала просроченное и
забытое, при равенстве раньше назначенное повторение, затем добор нового материала
в остаток времени. Без `combinations`. Ограничивает объём одной сессии, показывает
оставшийся долг, не создаёт бесконечную разминку. При отсутствии подходящей среды
даёт вариант на воспроизведение или разбор результата с честной маркировкой.

  синтетические. Перед коммитом контент проходит `scripts/secret_scan.py`.
- Состояние в SQLite: `CommandPracticeState`, `CommandAttempt`, `MissionRun`.
  Раздельно фиксируются: вспоминал без помощи; вспоминал с помощью; разбирал вывод;
  применял в среде; применял в другом варианте. Начальные интервалы после
  самостоятельных верных ответов: 1, 3, 7, 14, 30 дней, это проектные значения для
  настройки. Подсказанный ответ не продвигает самостоятельное воспроизведение,
  история реального применения не обнуляется из-за одной ошибки памяти. Повторная
  отправка того же завершения не создаёт дубль, черновик ответа сохраняется при
  уходе со страницы.
- Миграция только добавляет новые таблицы и сохраняет существующие данные.
  Тестируется на одноразовой копии базы. Применение к рабочей базе и обновление
  Windows требуют резервной копии и отдельного разрешения владельца.

### 9.5 Область и границы

- Полный цикл в v1 закрывает Linux-приёмы из текстовых мнемоник: терминал Coach
  подключён к Linux, реальная практика доступна.
- Windows это 16 из 27 мнемоник, но терминал подключён к Linux. В v1 Windows-приёмы
  получают только вспоминание и разбор результата, помеченные как репетиция.
  Реальное выполнение ждёт согласованный Windows-стенд (в навигаторе указан WS01 с
  браузерным доступом, его доступность не проверена). Интерфейс явно называет среду
  и тип достижения. До стенда команды остаются в очереди, но отметку «применено на
  Windows» получить нельзя.
- Скриншотные Task-источники подключаются отдельным поздним этапом с извлечением
  встроенных изображений и визуальной сверкой человеком, а не только OCR.
- Не создаём новый сайт, приложение или коллекцию конспектов, не сбрасываем
  прогресс, не заменяем WebGoat/Juice Shop, не расширяем `range-runner` до
  произвольного shell, не запускаем внешний AI и не отправляем материалы в облако.
- Не используем скорость, серию и очки как доказательство навыка.

### 9.6 Этапы реализации

Работа дробится на приостанавливаемые куски, каждый заканчивается приёмкой.

1. Этап 1: каталог Linux-приёмов из текстовых мнемоник; сущности
   `CommandTechnique`, `CommandPracticeState`, `CommandAttempt`; аддитивная
   миграция на копии базы; задание на вспоминание со ступенями подсказок;
   интервалы 1/3/7/14/30; recall grader; безусловный приоритет просроченного в
   планировщике. Приёмка: `scripts/quality.sh`, новые адресные тесты, миграция на
   копии, живой проход в браузере, независимый critic-code PASS.
2. Этап 2: миссии-расследования с mission grader версии 1 и панелью каталога
   рядом с заданием. Сюжет «Сорока: пропавшая улика»: в подготовленном каталоге
   несколько файлов и один полезный след, нужно найти файл, выбрать строку и
   объяснить её связь с задачей; используются встречавшиеся в Linux 01-04 `pwd`,
   `ls`, `cd`, `find`, `file`, `cat`, `grep`, `cut` по мере задачи; на повторе
   меняются имя, расположение и содержимое, цель узнаваема, успех зависит от
   найденного результата и объяснения, а не от воспроизведения старого флага.
   Сюжет «Почему команда не сработала»: показана команда и ответ с намеренной
   ошибкой в учебных данных, нужно найти и исправить причину; типовые путаницы это
   имя против содержимого, текущая против постоянной переменной, CMD против Linux
   shell, флаг против аргумента; объяснение раскрывается только после ответа,
   случайный выбор варианта не считается самостоятельным вводом.
3. Этап 3: Windows-репетиции с явной маркировкой среды, панель покрытия,
   скриншотные Task-источники с извлечением изображений, OCR и визуальной сверкой.
   В сценарии прав доступа (Windows 07-08, `whoami` и `icacls`) упражнение сначала
   требует определить действие: официальный справочник описывает и просмотр, и
   изменение («Displays or modifies discretionary access control lists»,
   [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)),
   поэтому право на изменение учебной системы проверяется отдельно от чтения.

### 9.7 Готово, когда (для расширения)

1. Для каждого материала в принятой области есть решение по покрытию. Для
   скриншотов выполнена визуальная сверка, а не только OCR. Предварительный поиск
   названий не выдаётся за итоговый реестр.
2. Для каждого включённого приёма работают задание на воспроизведение и задание на
   объяснение результата. Реальное выполнение можно отложить статусом «ждёт
   стенд», карточка или репетиция не засчитываются как реальное применение.
3. Старт занятия, подсказка внутри миссии и повтор после перерыва работают в
   интерфейсе v2, прогресс переживает перезапуск, старые данные не теряются.
4. Ошибка, раскрытие ответа, самостоятельный ответ и подтверждённое выполнение
   дают разные результаты. Практический навык нельзя поднять просмотром или
   клиентским запросом с подставленным результатом.
5. Очередь проверена на приоритет просроченного, перенос даты, ошибку, помощь,
   отсутствие среды и повторную отправку. Рост каталога не вызывает перебор
   комбинаций.
6. Recall-ответ не исполняется, регистр и кавычки учитываются. Mission grader
   допускает заявленные корректные варианты и не принимает поддельный вывод. Прежний
   grader не ослаблен.
7. Роли и защита запросов сохранены. Входные поля, скрытые подсказки и результат
   проверяются на сервере. Чтение справочника не становится доказательством
   самостоятельного ответа.
8. Проходят `scripts/quality.sh`, адресные новые проверки, секрет-скан контента,
   миграция на тестовой копии и независимый critic-code с финальным PASS.
   Установок зависимостей и записи в рабочую базу без отдельного разрешения нет.
9. Проверены видимый учебный цикл и подсказки в браузере. Реальный Windows-релиз,
   подключённая Linux VM и первое прохождение пользователя это отдельные
   обязательные проверки перед заявлением «встроено и доступно в полигоне».

### 10.1. Цель

Сделать результат Cyber Range Coach проверяемым для одного ученика: условие
достаточно для ответа, ошибка не получает зачёт, показанная помощь учитывается,
а интервал повторения растёт только после разрешённой самостоятельной проверки.

Исправляются шесть подтверждённых проблем. Идентификаторы ниже сохраняются в
задачах, проверках и отчёте реализации.

| ID | Подтверждённое поведение | Требуемое поведение |

| CRC-01 | Условие чтения файла скрывает `briefing.txt`; условие grep скрывает файл и метку; задание переменной скрывает `NEXT_STEP`. | Все исходные данные видны до подсказок; ученик выбирает команду, а не угадывает данные. |

### 10.3. Входы, выходы и правила взаимодействия

#### A. Достаточное условие и приватный ответ (CRC-01)

Каждый из 169 приёмов получает публичный `context` с именованными синтетическими
исходными данными. Формат включает оболочку, исходный каталог при необходимости,
файлы/пути, искомые значения и ограничения задачи. Поля заполняются по смыслу
конкретного приёма; пустые обязательные данные являются ошибкой контента.
Команда и инструкция по её сборке в `context` не включаются.

Например, условие для `cat` содержит «Текущий каталог содержит текстовый файл
briefing.txt. Покажите его содержимое целиком». Условие для `grep` сообщает
файл briefing.txt, метку CRED и требование вывести совпавшие строки. Условие
переменной называет NEXT_STEP и требует её значение, не буквальное имя.

Выход API плана содержит `prompt`, `context`, публичный контракт полей ответа,
названия ступеней помощи и `challenge_version`. Допустимые команды, ожидаемые
значения структурированного разбора, sample_answer и тексты закрытых подсказок
остаются на сервере. Данные не должны утекать через запасной маршрут чтения
каталога или описание схемы.

Валидатор проверяет объявленные обязательные переменные условия и разрешимость
ссылок. Ручная содержательная сверка всех 169 заданий проверяет, что ни один
обязательный аргумент не остаётся только в приватном ответе. Одна лишь проверка
вхождения строки не считается доказательством достаточности условия.

#### B. Проверка команды без исполнения (CRC-02)

Вход: введённая строка, оболочка, версия задания, явные допустимые ответы и
серверная история помощи текущего цикла. Выход: текущие причины результата
`correct`, `correct_with_help`, `wrong_tool`, `wrong_flag`, `wrong_shell`,
`insufficient_data`, дополненные адресным объяснением ошибки.

Для Bash первичный безопасный путь проверки состоит в точном совпадении с одним
из явно заданных ответов. Дополнительное сравнение использует лексическое
представление, сохраняющее текст, вид кавычек, экранирование, границы слов,
операторы и участки раскрытия переменных/шаблонов. Нельзя использовать результат
`shlex.split(posix=True)` как доказательство эквивалентности команд.

Разрешается нормализовать только разделители слов вне кавычек и только там,
где разбор установил их роль. Регистр, пробелы внутри кавычек, перенаправления,
конвейеры, `&&`, `;`, `$`, `*` и обратные слэши не теряются. Перестановка групп
флагов допускается лишь по контракту конкретного задания. Для сложного синтаксиса,
который дополнительный разбор не поддерживает, засчитываются только явно
перечисленные строки; неизвестная форма не получает автоматический успех.

Каждому из 73 Bash-приёмов сопоставляется поддерживаемый режим сравнения.
Неподдерживаемый, но возможно корректный вариант получает `insufficient_data`
с текстом «Этот вариант пока не поддерживается автоматической проверкой».
Это ограничение проверяющего модуля, а не утверждение, что Bash-команда неверна.
Для такого исхода API дополнительно возвращает `verification_status=unverified`.
Он не устанавливает completed_at, не считается ошибкой/забыванием, не меняет
interval_index, next_due_at, eligible_at и право текущего окна на самостоятельный
зачёт. Сохраняются черновик и техническое событие. Ученик может изменить только
форму записи в том же окне; обычные правила помощи продолжают действовать.
Пустой ответ, «не помню» и доказанная ошибка синтаксиса имеют обычный учебный
результат, а не технический `unverified`. Ветвление по одному `correct=False`
для этих случаев запрещено. Аналогично `input_not_verifiable` терминала не
считается забыванием команды и не меняет recall-расписание.
Вызовы shell, `eval`, subprocess или внешнего AI для проверки ответа запрещены.

Существующие cmd-контракты сохраняются: обратные слэши путей, кавычки вокруг
пробелов, нормализация регистра имени команды и ключа, значимый регистр аргумента
после двоеточия. Нормализация Bash не применяется к Windows.

Техническое основание различения кавычек: одинарные кавычки сохраняют буквальное
значение каждого символа, двойные допускают определённые раскрытия. См.
[GNU Bash, Single Quotes](https://www.gnu.org/software/bash/manual/html_node/Single-Quotes.html)
и [Double Quotes](https://www.gnu.org/software/bash/manual/html_node/Double-Quotes.html).
В данной системе это основание для консервативной проверки, а не обещание
реализовать полный интерпретатор Bash.

#### C. Проверяемый разбор и свободное объяснение (CRC-04)

Автоматическая проверка работает с ограниченными структурированными фактами.
Для разминки условие показывает отдельный синтетический пример вывода и задаёт
поля, необходимые для его разбора. Пример вывода показывается после фиксации
ответа на команду, чтобы не подсказать саму команду. Разбор вывода имеет собственное
завершение; он не может задним числом изменить зафиксированный recall-ответ.

Для миссии контракт определяет поля доказательства. Например, для «Сороки»:
`source_path`, `marker`, `sector`, фрагмент строки и идентификатор альтернативной
записи с конкретным признаком, по которому она не подходит. Ученик вводит значения
самостоятельно из публичного снимка. Приватные ожидаемые ответы не возвращаются
в схеме полей. Сервер проверяет значения и их связь с одним вариантом источника,
а не наличие слов «маркер» и «сектор» в произвольном тексте.

Конкретный набор полей задаётся для каждого из семи вариантов миссий и каждого
включённого observation-задания. Не применяется один общий шаблон, который
подходит только к миссии «Сорока». Допустимые значения и эквиваленты задаются явно.
Если контракт ещё не переведён, результат остаётся `unexplained` или `needs_review`;
такой контракт не входит в завершённую поставку этого раздела.

Свободное объяснение сохраняется для собственного рассуждения и вопроса
наставника. Оно получает `free_text_review_status=not_assessed`. Нельзя выводить
«объяснение подтверждено» только по ключевым словам или длине текста.
`solved` означает «Артефакт и структурированный разбор подтверждены».
Рядом явно указано «Свободное объяснение сохранено, автоматически не оценено».
Противоречие в свободном тексте не объявляется обнаруженным, если модуль его
фактически не проверял. Эта граница относится к синтетической учебной задаче,
а не к доказательству выполнения команд на настоящем стенде.

Отправка только прежнего свободного текста, включая оба примера CRC-04, не
создаёт `solved` и не устанавливает `output_interpreted_at`. Неизвестная связь
возвращает `needs_review`; неверные обязательные факты дают адресную ошибку.
Результат recall и разбор вывода сохраняются раздельно. Верная команда сама по
себе не означает правильного понимания вывода.

#### D. Достоверная регистрация терминальной строки (CRC-03)

Сохраняются настоящий интерактивный SSH-терминал, resize, reconnect и read-only
transcript на телефоне. `range-runner` не получает общего shell и не расширяет
список разрешённых команд.

Регистратор заменяет простое накопление символов на ограниченный автомат
редактирования строки. Он хранит текст, позицию курсора, незавершённую управляющую
последовательность между WebSocket-кадрами и статус достоверности. Обязательная
поддержка: обычный ввод, Backspace, Delete, Left/Right, Home/End, Ctrl+A/E,
Ctrl+U/K, очищение незавершённой строки после Ctrl+C, вставка текста без перевода
строки. Событие Enter фиксирует окончательную строку, а не сырые нажатия.
Конфигурация редактирования проверяемой сессии должна быть известна регистратору;
другая раскладка Readline, vi-mode или пользовательское переназначение клавиш
не могут молча считаться поддержанными.

Перед допуском проверяемого ввода backend создаёт отдельную интерактивную
Bash-сессию `student` с PTY и временным профилем текущего процесса. Направление
запуска: `INPUTRC=/dev/null bash --noprofile --norc -i`, затем служебная
инициализация Emacs-режима и поддерживаемых привязок клавиш. Исполнитель
подтверждает на целевой Linux VM точную команду запуска и набор привязок.
Профиль не записывается в .bashrc, .bash_profile, .inputrc или системные файлы;
его действие заканчивается вместе с этой SSH-сессией.

Сервер блокирует пользовательские input-кадры до завершения своей инициализации,
считывает фактический режим и поддерживаемые bindings из той же Bash-сессии
и проверяет их по контракту. Ответ связывается с текущей сессией одноразовым
идентификатором, а не поиском общего текста в transcript. Служебные команды
инициализации не становятся командами ученика; граница их вывода фиксируется
до первого пользовательского input. Только после подтверждения профиля
`input_integrity` становится достоверным. Невозможность запуска Bash или проверки
bindings оставляет терминал доступным для незачётной практики с объяснением.
Утверждение «все 19 уроков проходят» допустимо только после успешной проверки
этого профиля. Временная инициализация данной сессии входит в согласуемый scope,
постоянные настройки пользователя и права range-runner остаются прежними.

Программа не должна делать вид, что полностью воспроизводит Readline. История
shell до текущего run, Tab completion, произвольные макросы, многострочная
вставка и неизвестные управляющие последовательности требуют отдельного
доказанного восстановления. Пока оно отсутствует, raw-ввод продолжает работать,
но попытка получает `input_not_verifiable` и понятное предложение начать чистую
проверяемую попытку. Нельзя отнести неопределённость регистратора к ошибке ученика.
Неоднозначное редактирование не исправляется подстановкой ожидаемой команды.

Входы интерактивной программы, включая шесть ответов урока evidence-report,
помечаются отдельно от запуска shell-команды. Нажатия управления программой
не должны превращаться в новые shell-команды. Если границу нельзя установить,
успешный зачёт блокируется с технической причиной, а не ложным verdict.

Transcript/probe grader требует достоверный ledger, первую утверждённую команду
чистого run и прежние проверки результата. Перезапуск соединения, обрезание
transcript или усечение истории не могут превратить использованную попытку в
чистую. Недостоверность сохраняется до явного reset с новым run. Реализация
должна доказать совпадение восстановленной строки с фактически выполненной
командой в интеграционной SSH-проверке; тест одного парсера недостаточен.

Штатная семантика редактирования описана в
[GNU Bash, Commands For Moving](https://www.gnu.org/s/bash/manual/html_node/Commands-For-Moving.html)
и [Commands For Killing](https://www.gnu.org/s/bash/manual/html_node/Commands-For-Killing.html).
Выбор ограниченного автомата и честного отказа при неизвестном вводе является
проектным решением этого раздела.

#### E. Показ справки и учёт помощи (CRC-05)

У владельца одна общая учебная история на всех привязанных устройствах.
При открытии самостоятельной попытки сервер создаёт или возобновляет окно
проверки. Пересекающиеся карточки миссий и справочника не выдаются одновременно
с проверяемым заданием автоматически. Каталог остаётся доступен через явное
действие «Открыть справку, ответ будет с помощью».

Сервер выдаёт содержание справки только после фиксации события раскрытия.
Событие связано с technique_id, версией задания, окном проверки, временем и
поверхностью (`hint`, `technique_card`, `mission_reference`). Помощь из другой
вкладки и другого привязанного устройства относится к той же учебной истории.
Новый attempt_key, reload или смена экрана не удаляют событие.

API плана миссий отдаёт идентификаторы справочных карточек и нейтральные метки
до их открытия. Содержимое карточек возвращает отдельная операция раскрытия;
GET плана не меняет прогресс. Для существующих чтений необходимо проверить все
маршруты выдачи команд и ответов. Доступ viewer к теории сохраняется, но во время
активной самостоятельной проверки защищённое пересекающееся содержание для него
также скрыто; viewer не получает права самостоятельно создавать учебные попытки.

Материал, уже раскрытый интерфейсом Coach до старта попытки, учитывается в окне
выдержки из пункта F. Если сервер не может сопоставить справку одному приёму,
событие помечает весь набор приёмов этой карточки. Публичный учебный пример,
содержащий полный допустимый ответ, обрабатывается так же. Это не запрет на
чтение документов вне Coach: внешнее чтение приложение не наблюдает и не обещает
контролировать. Подпись результата: «Самостоятельный ответ в Coach».

#### F. Серверный цикл повторения (CRC-06)

Предлагаемое правило для согласования: после зачёта с помощью или раскрытия
готового решения следующая самостоятельная проверка возможна не раньше чем
через 24 часа. Это продуктовый параметр, а не установленный научный норматив.
Интервалы 1/3/7/14/30 дней сохраняются как действующие проектные значения §9.4.

Сервер начинает самостоятельное окно, только если наступил `next_due_at` и
истёк срок после последней помощи; для нового, ранее не раскрывавшегося приёма
окно доступно сразу. Клиент не задаёт право на продвижение, номер цикла или
текущее время. До наступления срока доступна дополнительная репетиция с подписью
«Тренировочный повтор, интервал не увеличится».

При первом правильном самостоятельном завершении сервер атомарно закрывает
окно, увеличивает интервал на одну ступень и назначает следующий срок от своего
времени. Правильный ответ с помощью не увеличивает индекс и назначает повтор
через сутки. Ошибка не увеличивает индекс, ставит повтор в текущую сессию и
сохраняет факт помощи. В одном окне после ошибки можно повторить ответ, но такой
успех считается тренировочным, а не самостоятельной проверкой; следующее
самостоятельное окно доступно через сутки. Наличие ошибки/помощи не стирает
историю реального применения в среде.

Дополнительные повторы до срока сохраняются в истории, но не увеличивают
индекс, не пишут новую отметку самостоятельности и не отодвигают срок бесконечно.
Новое явное раскрытие справки обновляет срок выдержки после помощи; это отдельное
показанное пользователю событие, а не эффект повторного сетевого запроса.

Один idempotency_key возвращает исходный сохранённый результат. Новый ключ в
закрытом или ещё не разрешённом окне создаёт только тренировочный результат.
При конкурентных запросах, включая два разных устройства, допускается не более
одного изменения интервала на окно. Нужны транзакция и ограничение уникальности
в SQLite; проверки только в интерфейсе или process-local lock недостаточно.
То же правило действует при создании окна: срок перепроверяется внутри
транзакции, а уникальность активного самостоятельного окна одного приёма
обеспечивается базой. Два одновременных старта не создают два права на зачёт.
Запрос раскрытия помощи и завершение попытки сериализуются относительно одного
окна. Сервер сначала регистрирует раскрытие и только затем возвращает материал.

### 10.4. Данные и совместимость

Контент остаётся в двух YAML-каталогах команд и одном каталоге миссий. Для
изменённых заданий повышается версия. Старые идентификаторы приёмов, адреса
источников и ручные изменения Windows-каталога сохраняются. Автоматическая
перегенерация YAML из DOCX в эту работу не входит.

Новые логические данные, окончательные имена полей согласуются с моделями при
реализации без изменения смысла:

| Данные | Поля и назначение |
|---|---|
| Публичное условие | `context`, именованные входные значения, пример вывода для отдельного разбора, публичная схема структурированного ответа. |
| Версия проверки | `challenge_version`, `grader_version`, `grading_policy_version`, версия сравнения команд. |
| Окно проверки | `window_id`, technique_id, версия задания, opened_at, eligible_at, closed_at, результат, признак единственного продвижения. |
| Событие помощи | event_id, technique_id, window_id при наличии, shown_at, поверхность, объём раскрытия; повтор одного события не дублируется. |
| Попытка | Существующий ключ плюс window_id, тип `assessment`/`rehearsal`, structured_observation, исходный результат и интервал. |
| Миссия | Структурированные факты, отдельный свободный текст, `free_text_review_status`, версия проверяющей политики. |
| Терминал | Курсор и состояние парсера активной сессии; устойчивые `input_integrity` и причина неопределённости у run. |

Миграция аддитивная и сначала выполняется на одноразовой копии. Исходные
`CommandAttempt`, `MissionRun`, Evidence, заметки и существующие даты не удаляются
и не переписываются. Старые зачёты отображаются как результаты прежней версии
проверки; им не присваивается задним числом более сильная гарантия. Автоматическое
обнуление прогресса и массовый пересчёт старых интервалов не выполняются.

Для старого состояния без окна проверки сервер использует существующий due_at.
Если дата помощи доступна, eligible_at не раньше этой даты плюс сутки. Если
история помощи неизвестна, первая новая самостоятельная проверка допускается
не ранее суток после первого обращения к этому приёму под новой политикой;
интерфейс объясняет однократную выдержку, история при этом сохраняется.

Открытая попытка старой версии контента сохраняется как черновик, но не
завершается против незаметно изменённого контракта. Сервер возвращает
`challenge_version_changed`; интерфейс показывает сохранённый ответ и предлагает
начать актуальное задание. Закрытые старые попытки по прежнему ключу возвращают
свой исходный результат без нового зачёта.

Время хранится в UTC, показывается в локальной зоне устройства. Для сравнения
используются серверные timestamps, а не клиентская дата или строка часового пояса.
Идентификатор устройства можно использовать для диагностики гонки, но он не
создаёт отдельный прогресс второго ученика.

### 10.5. Сквозные сценарии

1. **Первое самостоятельное решение.** Ученик открывает достаточно определённое
   условие, вводит команду, сервер фиксирует ответ. Затем показывается синтетический
   вывод и поля его разбора. Результаты «вспомнил команду» и «разобрал вывод»
   различаются. После допустимого самостоятельного зачёта назначается следующий
   срок. Reload восстанавливает ту же попытку и не открывает новый зачётный цикл.
2. **Подсказка и повтор.** Ученик раскрывает карточку миссии в другой вкладке.
   Сервер записывает помощь до выдачи текста. Правильный ответ в разминке получает
   «с помощью». Немедленные повторные ответы остаются репетицией. После истечения
   суток и наступления due_at новая самостоятельная проверка может продвинуть
   интервал ровно один раз, включая одновременные запросы с Mac и Windows.
3. **Исправление команды.** В чистой лаборатории ученик исправляет опечатку через
   Ctrl+U или перемещение курсора и выполняет `pwd`. Журнал содержит фактически
   выполненную команду; grader применяет прежние требования к первой команде и
   результату. Неизвестный ввод даёт техническое объяснение и явный reset,
   но не ложный «неверный инструмент». Шесть ответов evidence-report сохраняются
   как ответы программы и не нарушают границу shell-команды.
4. **Разбор миссии.** Ученик находит артефакт, самостоятельно заполняет факты
   из текущего снимка и пишет объяснение. Неверная связь вызывает адресную ошибку;
   набор ключевых слов без фактов не даёт `solved`. При верных фактах показывается
   ограниченный смысл зачёта. Свободная проза сохранена и не объявляется
   автоматически проверенным пониманием.

### 10.6. Не-цели

- Новые курсы, миссии, Windows-стенд, OCR скриншотов и панель покрытия Этапа 3b.
- Полный парсер Bash/cmd, полноценная реализация Readline или универсальное
  понимание естественного языка.
- Замена интерактивного SSH-терминала только полем ввода, расширение полномочий
  `student`/`range-runner`, изменение Docker, Firewall или сертификатов.
- Внешний AI, передача DOCX/логов в облако и новые платные зависимости.
- Автоматический пересмотр прошлых Evidence, очистка базы, перенос пользовательских
  документов и пересоздание проекта.
- Подтверждение применения Windows-команд на основе браузерной репетиции.

### 10.7. Доступы и решения владельца

Для подготовки спецификации дополнительные доступы не нужны. Для локальной
реализации и проверок достаточно текущего репозитория и одноразовой базы.
Настоящий SSH-сценарий требует доступного пользовательского учебного Linux-хоста
с уже настроенными `student`, `range-runner` и сверенным host fingerprint.
Секреты берутся только из существующего защищённого механизма, в документы не
копируются. До предоставления стенда этот пункт приёмки остаётся открытым.

Перед реализацией согласуются предложенные решения: ограниченный терминальный
регистратор с честным отказом при неизвестном вводе; структурированный разбор
с непроверенной свободной прозой; сутки выдержки после ошибки/помощи; сохранение
старых результатов с маркировкой версии. Эти параметры не выдаются за уже
принятые пользователем решения.

Применение миграции к рабочей базе, установка зависимостей при необходимости,
обновление Windows и публикация изменений выполняются по отдельному разрешению
владельца. Подготовка текста спецификации не запускает эти действия.

### 10.8. Готово, когда

| Проверка | Наблюдаемый критерий |
|---|---|
| AC-01 / CRC-01 | Сверены все 169 условий; для каждого обязательного аргумента есть публичный источник. У `cat`, `grep`, переменной и Windows-путей можно ответить без угадывания и без полной подсказки. Реестр 27 источников и 2237 адресов не потерян. |
| AC-02 / CRC-02 | Оба примера с неверными кавычками из CRC-02 не получают `correct`; явно допустимые формы, пробелы, флаги и все текущие cmd-примеры проходят адресные проверки. Recall никогда не исполняет ответ. Для каждого Bash-задания задан поддерживаемый режим. Неподдержанная форма возвращает unverified без штрафа и допускает исправление формы в том же окне. |
| AC-03 / CRC-03 | В настоящем PTY/SSH Ctrl+U, Left/Right, Home/End, Delete, Backspace, Ctrl+A/E/K/C и разрыв escape-последовательности между кадрами дают правильный ledger. Tab/неизвестная история/многострочная вставка не дают ложный зачёт. Reconnect, обрезание и reset проверены отдельно. Подтверждение временного профиля проверено со стандартными и намеренно изменёнными bindings/vi-mode. До подтверждения пользовательский ввод не принимается как проверяемый. Все 19 уроков, включая evidence-report, сохраняют возможность полного прохождения. |
| AC-04 / CRC-04 | «маркер сектор» и отрицание связи без обязательных фактов не дают `solved`. Неверный путь, маркер, сектор и смешение вариантов отвергаются. Полный правильный структурированный разбор проходит. Свободная проза не получает отметку автоматической проверки. Все семь вариантов и 169 observation-контрактов переведены. |
| AC-05 / CRC-05 | Во время самостоятельного окна ни Today, ни миссия, ни чтение карточки через API не раскрывают связанный ответ без события помощи. Проверены другая вкладка, reload и второе устройство. Viewer не получает новых полномочий. |
| AC-06 / CRC-06 | Пять немедленных новых ключей после раскрытия ответа не увеличивают интервал. До due_at он не растёт; после due_at и срока выдержки растёт один раз. Повторные и конкурентные завершения/раскрытия не обходят правило. Дополнительные репетиции не создают бесконечную отсрочку. Нейтральный unverified не меняет даты и окно. Два одновременных старта не создают два права на зачёт. Проверки используют управляемые серверные часы. |
| AC-07 / Совместимость | Миграция на копии сохраняет записи, заметки, evidence, даты и происхождение контента. Старый результат не переписывается. Версия изменённого черновика обнаруживается. Windows остаётся `awaiting_stand`, где реальное выполнение отсутствует. |
| AC-08 / Качество | `scripts/quality.sh` проходит в документированном окружении, включая контент, типы, сборку и отрицательные проверки. Мутации каждого исправления возвращают соответствующий дефект и роняют адресный тест. Независимый critic-code завершает проверку с PASS. |
| AC-09 / Интерфейс | Пройдены сценарии 10.5 с настоящим backend и временной базой: правильный/неправильный ответ, подсказка, сохранение, reload, возврат, повтор после срока. Проверены 390 и 1366 px с реальными данными; прежние контрольные ширины автотестов сохранены. Подставные ответы API не заменяют эту проверку. |

Базовый результат аудита 05.09.2026: 82 pytest, 10 Vitest и 17 Playwright прошли
с `PYTHONPATH=backend/src`, при запрещённой автоматической пересинхронизации
окружения. Без этого пути наблюдался `ModuleNotFoundError`. Перед приёмкой
исполнитель отдельно устанавливает причину отсутствия импорта и документирует
воспроизводимый запуск из lock-файлов. Успешный прогон с дополнительным путём
не объявляется доказательством готовности обычного launcher.

Техническую готовность исходников и доступность в реальном полигоне сообщают
раздельно. Windows installer, полный маршрут Windows/Linux/Docker и устройство
пользователя проверяются после необходимых разрешений. До этого допустим итог
«локально проверено, проверка стенда открыта», но не «доступно в полигоне».

## 11. Расширение v2.2: качество учёбы, лестница навыков, понятная теория

Статус: утверждено владельцем 24.09.2026 («ок, начинай»). Разделы 1-10
действуют без изменений, кроме пункта 10.3 C в части показа данных миссии
(см. 11.3 Б). Пометка «[предположение]» означает решение по умолчанию,
которое владелец может поменять до начала кода.

Основание: проверка пригодности к учёбе
[docs/learning-fitness-2026-09-24.md](docs/learning-fitness-2026-09-24.md).
Проверено там же на данных: у всех 169 приёмов поле
`observation.example_output` содержит заглушку `SYNTHETIC RESULT`; миссия
«Сорока» засчитана без единой команды, потому что содержимое файлов показано
на экране; после неверного ответа в разминке правильный ответ не показан. В
[curriculum/fundamentals.yaml](curriculum/fundamentals.yaml) каждому из 19
навыков соответствует ровно одна практика, поэтому последовательного роста
навыка в курсе нет.

### 11.1. Цель

Ученик, начав с нуля, растит каждый навык ступенями от «делаю с подсказкой» до
«делаю сам на новой задаче», и на каждой ступени сначала получает теорию,
понятную школьнику 10-12 лет, а зачёт получает только за то, что сам сделал
в терминале.

### 11.2. Части системы

| Часть | Зачем |
|---|---|
| Настоящие примеры вывода | Заменить 169 заглушек выводом, снятым с эталонной машины, чтобы разбор вывода учил читать настоящий вывод. |
| Файлы миссии в Linux-терминале | Миссия раскладывает свои файлы в домашний каталог `student`, экран показывает только задачу. Ответ добывается командами. |
| Разбор ошибки в разминке | После неверного ответа показать правильную команду и одну фразу «почему», зачесть как помощь. |
| Простая теория | Новый блок у каждой практики и каждого приёма, написанный для школьника. Прежняя теория остаётся как «Подробнее». |
| Лестница навыка | У каждого навыка 3 ступени практик вместо одной, навык поднимается только по пройденной ступени. |
| Новый трек «Уровень 2» | Новые навыки поверх базы, на своём стенде и в своей Linux VM. |
| Автопоиск стенда | Адреса ноутбука, Mac и Linux VM и пути к мишеням находятся сами, без настройки роутера. |
| Проверки содержания | Валидатор отклоняет заглушки, считает ступени, проверяет простоту теории. |

### 11.3. Входы, выходы, правила

#### А. Настоящий вывод (дефект Д1)

- Bash, 73 приёма. Вход, команда приёма и учебные данные условия. Скрипт
  разработчика выполняет её в эталонном Ubuntu 24.04 от пользователя
  `student` и записывает вывод в `observation.example_output`. Выход,
  настоящий вывод с заменой имени машины и пользователя на учебные значения.
- cmd.exe, 96 приёмов. Снимаются на Windows-ноутбуке отдельным скриптом
  `scripts/capture-windows-outputs.ps1`, который только читает систему и
  сохраняет файл для переноса. Пока снимка нет, приём остаётся
  `awaiting_stand` и показывает «Пример появится после снимка со стенда», а не
  заглушку.
- Поля структурированного разбора ссылаются на строки настоящего вывода.
  Подписи полей не содержат ожидаемый ответ (сейчас подпись
  «os name / название / имя системы» его выдаёт).

#### Б. Миссия только через терминал (дефект Д2)

- Экран миссии показывает легенду, задачу и корень дерева (`~/missions/<вариант>`),
  без содержимого файлов. Это заменяет показ «публичного снимка» из 10.3 C.
- Кнопка «Подготовить файлы» вызывает новое разрешённое действие
  `range-runner mission-seed <вариант>`. Оно создаёт файлы только внутри
  `/home/student/missions/` и ничего не удаляет вне этого каталога.
- Зачёт прежний, по структурированным фактам. Дополнительно требуется, чтобы в
  журнале терминала этой попытки была команда, прочитавшая подтверждающий файл.
- Без подключённого Linux (телефон, Mac без VM) миссия доступна только для
  чтения легенды, с пометкой «нужен терминал».

#### В. Разбор ошибки в разминке (дефект Д3) и Enter

- Неверный ответ, затем экран «Правильно так», правильная команда, одна фраза
  «почему» и типичная ошибка из каталога. Это событие помощи по правилам 10.3 E,
  интервал не растёт, повтор назначается на завтра.
- Enter отправляет ответ, Shift+Enter переносит строку.

#### Г. Простая теория

Новый блок `simple_theory` у каждой практики и каждого приёма:

| Поле | Содержание |
|---|---|
| `analogy` | Сравнение с бытом, 1-2 предложения («`pwd` как вопрос "в какой я комнате?"»). |
| `what_it_does` | Что делает команда, до 3 коротких предложений. |
| `words` | Каждое английское и профессиональное слово урока с объяснением простыми словами. |
| `picture` | Маленькая схема (текстом или SVG), где видно, что происходит. |
| `check` | Один вопрос «проверь себя» с ответом, который открывается кнопкой. |

Правила простоты, проверяемые валидатором: предложение не длиннее 15 слов;
английское слово или термин встречается только после объяснения в `words`;
нет сокращений без расшифровки. Прежние `term` и `worked_example` уходят в
раскрывающийся блок «Подробнее». Порядок экрана практики: простая теория, затем
пример, прогноз, действие, как в разделе 1.

#### Д. Лестница навыка

Каждый из 19 навыков получает три ступени практик:

| Ступень | Что делает ученик | Подсказки | Навык после зачёта |
|---|---|---|---|
| 1. С проводником | Та же задача, что сейчас, по шагам. | Все доступны | `guided` |
| 2. Сам | Новая задача с другими данными, шагов нет. | Только по кнопке, считаются помощью | `independent` |
| 3. Перенос | Та же идея в другой обстановке (другой каталог, другая цель, другой журнал). | Нет | `transfer` |

- Ступень открывается после зачёта предыдущей. Каталог для чтения остаётся
  открытым (10.3 E), но зачёт ступени 2 и 3 только по порядку.
- Ступень 2 или 3, пройденная с помощью, не поднимает навык и возвращается
  в очередь повторения.
- Поле `stage` урока расширяется значением `transfer`; сейчас там только
  `introduced`, `guided`, `independent`. Для навыков без Docker-цели перенос
  делается на других данных в Linux VM [предположение].
- Итого по базе, 19 существующих плюс 38 новых практик, плюс 3 ступени разведки из 11.3 З.

#### Е. Трек «Уровень 2» [предположение по составу]

Новые навыки, каждый сразу с тремя ступенями, по порядку:

1. Журналы и время событий в Linux (`journalctl`, `last`, сопоставление времени).
2. Хэши и целостность файлов (`sha256sum`, сравнение копий).
3. Процессы и открытые порты своей машины (`ps`, `ss`).
4. Поиск признаков повышения прав в своей VM (`sudo -l`, SUID, `cron`), только чтение.
5. Web, SQL-инъекция в уроке WebGoat своего стенда.
6. Web, XSS в Juice Shop своего стенда.
7. Web, доступ к чужому объекту (IDOR) в Juice Shop своего стенда.
8. Итоговое расследование, объединяющее навыки 1-7 с отчётом.

Навыки 5-7 проверяются по наблюдаемому состоянию стенда. Для Juice Shop это
отметка решённой задачи через его API списка задач [не подтверждено,
проверяется на PoC до написания уроков]. Если детерминированной проверки нет,
урок не входит в поставку, а не проверяется по словам ученика.

#### Ж. Автопоиск стенда без настройки роутера

Владелец не настраивает роутер и не вводит адреса. Адреса и пути находятся
при каждом запуске.

| Что сейчас задано жёстко | Где | Что будет |
|---|---|---|
| Адрес ноутбука `192.168.10.10` | `server.py` строка 24, лабы v1 в `content/labs/` | Mac ищет стенд в своей подсети по отпечатку сервиса (WebGoat отвечает переадресацией на `/WebGoat/login`, у Juice Shop заголовок страницы «OWASP Juice Shop»). Последний найденный адрес запоминается и проверяется первым, при неудаче поиск повторяется. |
| Адрес Mac `192.168.10.3` | правило брандмауэра Windows «CyberLab LAN only (Private, Mac)» | Правило пропускает любой адрес своей подсети (`LocalSubnet`) и только в профиле Private, как уже сделано для порта 8443. |
| Адрес Linux VM (WSL) | правило relay в [configure-firewall.ps1](installer/windows/configure-firewall.ps1) | Академия при каждом старте берёт текущий адрес WSL и сверяет его с правилом. Способ, не требующий прав администратора при каждом запуске (например, правило по виртуальному адаптеру WSL, а не по адресу), выбирается на PoC [не подтверждено]. |
| Выбор своего адреса для relay | [targets.py](backend/src/cyber_range_coach/routers/targets.py) `_connect_host` берёт первый частный адрес | Берётся адрес интерфейса, через который реально виден адрес Linux VM, а не первый в списке. |
| Пути к мишеням (`/WebGoat/`, `/`) | лабы v1, тексты уроков | Путь определяется запросом к найденному порту по тому же отпечатку, в урок подставляется найденный. |

Для второго устройства (Mac, телефон) после привязки: если академия не
отвечает по прежнему адресу, клиент ищет порт 8443 в подсети и принимает
только сервер с тем же отпечатком сертификата, который закреплён при привязке.
Чужой сервер с тем же портом не принимается.

Границы поиска: только своя подсеть /24, только TCP-подключение к известным
портам (8080, 3000, 8443), не чаще одного полного поиска в минуту. Это
проверка своего стенда, а не сканирование сети.

#### З. Лаба «Разведка: найди свой стенд»

Поиск стенда одновременно служебная функция (Ж) и учебное задание. Академия
ищет стенд сама и молча, потому что ей нужен правильный ответ для зачёта и
адрес для остальных практик, даже если ученик в разведке ошибся. Ученик
ищет тот же стенд своими командами, и его находки сверяются с найденным
академией в момент попытки.

Место в курсе, новый навык `recon-discovery` после урока `network-ip-route`
(order 70) и перед `tcp-reachability` (order 90). Три ступени по правилам Д:

| Ступень | Задача | Команды | Зачёт |
|---|---|---|---|
| 1. С проводником | Узнать свой адрес и шлюз, понять, где живёт машина со стендом. | `ip -brief address`, `ip route` | Введённые адрес и шлюз совпали с выводом этой попытки. |
| 2. Сам | Найти открытые порты на найденной машине в разрешённом диапазоне. | `nmap -p <диапазон> <адрес>` | Список портов совпал с тем, что академия видит сейчас. |
| 3. Перенос | Узнать, какой сервис на каждом порту и по какому пути он отвечает. | `nmap -sV`, `curl -I` | Для каждого порта верно названы сервис и путь (например, `/WebGoat/`). |

Правила:

- Разрешённая область задаётся в начале лабы, как в уроке
  `scope-fact-hypothesis`: только своя машина со стендом и только показанный
  диапазон портов. Сканирование других устройств домашней сети (телефоны,
  телевизор) в зачёт не входит и в задании не просится.
- Адрес и порты меняются вместе с реальным стендом, поэтому заучить ответ
  нельзя, его каждый раз надо найти заново.
- Зачёт требует и журнал терминала с командой поиска, и введённые факты,
  как в миссиях (11.3 Б).
- Ученик работает в Linux внутри Windows (WSL), а мишени стоят на той же
  Windows. Поэтому «найти машину» здесь значит найти шлюз, а порты мишеней
  видны через relay академии. Как именно WSL видит порты Windows в текущем
  сетевом режиме, проверяется на PoC до написания уроков [не подтверждено].
- Разведку всей домашней сети с Mac (поиск ноутбука среди устройств)
  предлагаю позже, отдельной лабой Уровня 2, потому что Mac в академии не
  имеет проверяемого терминала [предположение].

### 11.4. Данные

- `curriculum/fundamentals.yaml`: новые уроки ступеней 2 и 3, блок
  `simple_theory` у всех уроков.
- `curriculum/level2.yaml`: новый трек из 11.3 Е.

### 11.5. Сценарии

1. Новичок открывает «Где я нахожусь», читает простую теорию с картинкой
   комнат, отвечает на «проверь себя», делает `pwd` по шагам (ступень 1).
   Завтра получает ступень 2 с другим каталогом без шагов, проходит сам, навык
   становится `independent`.
2. Разминка, ученик пишет `ls` вместо `pwd`, видит «Правильно так: pwd,
   потому что...», повтор завтра. Затем разбирает настоящий вывод `pwd`.
3. Миссия «Сорока», ученик нажимает «Подготовить файлы», в терминале ищет
   строку через `find` и `grep`, вводит факты, получает зачёт. Переписать
   ответ с экрана нельзя, его там нет.
4. Уровень 2, SQL-инъекция на своём WebGoat, зачёт по состоянию урока на
   стенде после PoC-проверки способа.

### 11.6. Не-цели

- Не проверяем свободный текст ИИ и не оцениваем объяснения автоматически (как в 10.3 C).
- Не атакуем ничего вне своего стенда и своей Linux VM.
- Не делаем озвучку, видео и мультипликацию теории.
- Не переписываем прежнюю взрослую теорию, она остаётся как «Подробнее».
- Не делаем мультиучеников и родительский кабинет.

### 11.7. Нужно от владельца

- Запустить на Windows-ноутбуке `scripts/capture-windows-outputs.ps1` и
  передать полученный файл на Mac (96 примеров cmd.exe). Агент к Windows
  доступа не имеет.
- Прочитать 5 уроков простой теории на пробу и сказать, понятно ли. Простоту
  валидатор проверяет формально, понятность решает человек.
- Утвердить состав трека «Уровень 2».
- Один раз на Windows разрешить замену правила брандмауэра «CyberLab LAN only (Private, Mac)» на правило по своей подсети (системная настройка, делает владелец).
