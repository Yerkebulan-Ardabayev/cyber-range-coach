=== ЭТАП 7. Прогресс, снижение подсказок, Field Notes ===

7.1 Assistance level по blueprint F.1 и F.2.
- Уровни L4..L0: 100% Guided, 75, 50, 25, Independent. Что именно скрывается на каждом уровне, взять из таблицы F.1 дословно.
- Уровень применяется СЕРВЕРНО, тем же механизмом фильтрации приватных полей, что уже есть для гейта гипотезы. На L2 команда не приходит клиенту, пока не нажата кнопка раскрытия. Не прятать CSS-ом.
- Понижение помощи на один уровень при закрытии шага, ТОЛЬКО если одновременно: solution не раскрыт, подсказка 3 не запрошена, выбор на развилке верный. Иначе уровень остаётся и навык уходит в review_queue.
- Уровень никогда не повышается автоматически. Если навык провален три раза подряд, вернуть предложение поднять помощь, но применять только по явному действию пользователя.

7.2 Mastery 0..5 по blueprint F.3.
- 1 за прохождение на L4, 2 на L3, 3 на L2, 4 на L1, 5 на L0.
- ВАЖНО: уровень 5 ставится только если прохождение на L0 выполнено на цели, которую этот навык раньше не проходил. Значит у лабы должно быть поле target (например webgoat или juiceshop), а skill_progress должен помнить множество уже пройденных целей. Добавь таблицу skill_target(skill_id, target, first_passed_ts) или эквивалент.

7.3 Prerequisites по F.4: навык доступен, когда все его prereq_ids имеют level >= 2. Недоступный навык показывается в интерфейсе как закрытый с указанием, какой навык открыть сначала.

7.4 Review queue по F.6 и F.7: интервалы 1, 3, 7, 21 день. В очередь попадает НАВЫК, не лаба. На Today показывается максимум одна карточка повтора за сессию.

7.5 Field Notes.
- Запись создаётся автоматически при закрытии шага из данных попыток: дата, цель, гипотеза, команды, реальные результаты, вывод, ошибки, чему научился.
- Экран Notes: список записей, открытие записи, поле для дописывания одного абзаца от руки.
- Ничего не выдумывать в записи: только то, что реально лежит в attempt и observation.

7.6 Экран Progress: таблица навыков с уровнем 0..5, текущим уровнем помощи, датой следующего повторения и признаком доступности. Плюс честный счётчик «шагов закрыто без подсказок 2 и 3» как доля, это смысловой критерий из blueprint.

=== ЭТАП 8. Playbook engine ===

8.1 Playbook это ориентированный граф по blueprint G: {id, role, title, phases[{id, title, checks[], decision{question, branches[{answer, next, note}]}}]}.

8.2 ДВА РЕНДЕРА ОДНОГО JSON, это ключевое требование, не два написанных текста:
- Guided Mode: по одной фазе на экран, с объяснением зачем, вопрос задаётся до ответа.
- Field Mode: вся цепочка на одном экране, только названия фаз и checks, без объяснений.
- Переключатель режима на экране playbook.

8.3 Наполнить ТРИ playbook, по одному на роль, с реальным профессиональным содержанием из blueprint раздел G:
- red-network-recon (Red Team): Scope, Reachability, Ports, Services, Versions, Attack surface, Decision.
- blue-suspicious-login (Blue Team / SOC): Alert, Validate, Scope, Collect evidence, Timeline, Hypothesis, Confirm or reject, Containment decision, Documentation.
- dfir-host-triage (DFIR): Preserve, Collect, Timeline, Processes, Network, Persistence, Accounts, Artifacts, Hypothesis, Evidence, Conclusion.
Каждая фаза несёт 2-4 конкретных check и осмысленную развилку. Содержание должно быть профессионально корректным, а не заглушками вида «шаг 1».

8.4 Расширить tools/validate_content.py на playbook: обязательные поля, ссылочная целостность next между фазами, отсутствие висячих переходов.
