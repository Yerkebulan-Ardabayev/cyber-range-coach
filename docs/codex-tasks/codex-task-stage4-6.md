ЭТАП 5. Lab Runner и парсеры
- Четыре фазы одного шага по blueprint разделу E: THINK, EXECUTE, ANALYSE, DECIDE. В каждой фазе на экране ровно одно активное действие.
- ГЛАВНОЕ ТРЕБОВАНИЕ, гейт гипотезы должен быть СЕРВЕРНЫМ, а не косметикой на CSS: пока в attempt нет непустой hypothesis для этого шага, GET /api/lab/{id} и API шага НЕ ОТДАЮТ клиенту поля command, command_anatomy, solution, hints и decision_options. Их физически нет в JSON, который получил браузер. Проверить это curl'ом и показать в отчёте.
- POST /api/attempt {lab_id, step_id, hypothesis} → {attempt_id}. Пустая или пробельная гипотеза отклоняется с понятным сообщением.
- POST /api/attempt/{id}/output {raw} → {facts[], unparsed[], parser}. Парсеры на регулярных выражениях в parsers/: nmap -sV (порт, состояние, сервис, версия), curl -i и сырой HTTP-ответ (код статуса, заголовки), простой строчный лог. Парсер извлекает ТОЛЬКО то, что буквально есть в тексте, ничего не достраивает. Каждый факт несёт номер исходной строки. Всё неразобранное возвращается в unparsed[] и показывается пользователю честно, а не прячется.
- Факты пишутся в observation с kind='fact'.
- Экран ANALYSE показывает факты с номерами строк и счётчик неразобранных строк с кнопкой «показать».

ЭТАП 6. Наставник, подсказки, развилка
- POST /api/attempt/{id}/conclusion {text} → {named[], missed[], flagged_as_fact[], question}. Логика сравнения без ИИ: сверка текста пользователя с рубрикой шага expect[] и distractors[]. named это совпавшие пункты expect, missed это несовпавшие, flagged_as_fact это совпадения с distractors, то есть утверждения, которых нет в фактах и которые пользователь подал как факт. question это наводящий вопрос из данных шага. Наставник НИКОГДА не выдаёт решение.
- Вывод пользователя сохраняется в attempt.user_conclusion. Его гипотезы пишутся в observation с kind='hypothesis'.
- GET /api/hint/{lab}/{step}?level=1|2|3 отдаёт РОВНО один уровень и инкрементит attempt.hints_used. Уровень 2 не отдаётся, пока не запрошен уровень 1.
- Solution это отдельная ручка с явным подтверждением, её раскрытие ставит attempt.revealed_solution=1 навсегда.
- POST /api/attempt/{id}/decision {choice} → {correct, why, next_step}. Разбор объясняет не только верный вариант, но и почему уводит в сторону именно выбранный, если он уводит.
- Кнопка solution и подсказки НЕ на экране по умолчанию, они за явным действием.
- Фаза DEBRIEF в конце шага показывает принцип, ошибки из попытки и закрывает шаг: attempt.verdict проставляется, после чего запись становится неизменяемой существующим триггером.
