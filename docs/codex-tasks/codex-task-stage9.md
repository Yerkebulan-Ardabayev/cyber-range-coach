=== ТРЕБОВАНИЯ К КАЖДОЙ ЛАБЕ ===

Структура ровно как в lab-1-2: пять шагов think, execute, analyse, decide, debrief. Поля по kind, как требует нынешний tools/validate_content.py.

Методический чек-лист, ему обязана удовлетворять каждая лаба (это gate, а не пожелание):
- Есть конкретный контекст миссии и явная роль.
- Ровно одна цель шага, объяснено зачем.
- Ученик думает первым: шаг think задаёт вопрос, на который нельзя ответить, не подумав.
- Команда не появляется без контекста и разобрана по аргументам в command_anatomy, включая раздел когда НЕ применять.
- Сказано, что искать в выводе.
- Факты отделены от гипотез.
- Есть decision point с четырьмя вариантами, где первый вариант верный (движок так устроен), а остальные три это реалистичные ошибки, а не соломенные чучела.
- debrief несёт профессиональный принцип одной фразой.

КРИТИЧНО про рубрику наставника. Качество разбора целиком зависит от богатства рубрики. Для каждого шага analyse и decide:
- expect: 3-5 объектов {id, label, any_of, regex опционально}. В any_of класть НЕ ОДНО слово, а 4-8 реальных синонимов и словоформ, которыми ученик может это выразить, включая разговорные («веб-морда», «страница логина», «редирект», «перекидывает»).
- distractors: 2-3 объекта {id, label, markers, any_of, unsupported_products при необходимости}. Ловить типовые недоказанные выводы именно этой темы. Маркеры: точно, наверняка, значит, скорее всего, очевидно, явно.
- guiding_question: настоящий наводящий вопрос по теме шага, не служебный текст.
НЕ копировать рубрику из лабы 1.2, у каждой темы своя.

ЗАПРЕЩЕНО: служебные формулировки из blueprint в пользовательском тексте (никаких «см. макет E.4», «этап roadmap», «по спецификации»). Пользователь видит только учебный текст.
